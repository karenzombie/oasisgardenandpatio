# Agent Brief: Accept.js Sandbox Payment Integration (dev only)

## Goal
Replace the demo-mode "no payment required" checkout with a real Authorize.net
Accept.js card flow running against the **sandbox**, so the full path (card entry
to charge to recorded payment to zeroed balance) can be tested end to end in dev.

This is net-new payment capture. Today the checkout has no charge step: the
`/checkout` route creates an order with the full amount as balance due, and the
checkout page shows a "Demo mode, no payment required" placeholder. Nothing is
charged. You are building the missing payment step.

## Non-negotiable guardrails (read before touching anything)
1. **Sandbox / dev only.** Do not touch prod DB or prod env. Leave
   `AUTHNET_SANDBOX` unset so the existing config defaults to sandbox
   (`apitest.authorize.net`). Do not add or flip any prod flag.
2. **The transaction key is server-only.** `AUTHNET_TRANSACTION_KEY` must NEVER
   be exposed to the browser or any client-readable config or bundle. Only the
   API Login ID and the Public Client Key may reach the frontend.
3. **Never log card data.** Do not log the Accept.js opaque token value, full
   card numbers, or the transaction key. Last-4 and card type are fine.
4. **Charge the server-computed total only.** Never trust a client-supplied
   amount. The charge amount must be the total this same route already computes.
5. **No paid order on decline.** If the gateway declines, no completed payment is
   recorded, the cart stays intact, and the customer gets a clear error.
6. **Reuse existing structures.** Do not invent new tables. Use the existing
   `payments` table, the existing balance/deposit recompute helper, and the
   existing config pattern in `authorizeNet.ts`.
7. **Codegen is real work.** `PlaceOrderBody` is generated by orval from the spec.
   Add any new request field at the spec source and regenerate. Do not hand-edit
   generated files. A green typecheck is not proof; paste command output.
8. **Stop at every gate.** Do the current phase only, then stop and report. Do
   not start the next phase until Karen confirms. Do not batch phases.
9. **Stay in scope.** No saved cards, no wallets, no unrelated refactors, no
   changes to other routes. Only what this brief describes.

## Phase 1: Backend charge function
In `authorizeNet.ts`, add a charge function alongside the existing refund helper,
reusing the same `getConfig()` env pattern and sandbox endpoint.

- Input: the server-computed amount, plus the Accept.js opaque token
  (`dataDescriptor` + `dataValue`), plus order/customer reference fields as
  needed for the gateway request.
- Amount units: the gateway expects a dollar amount string (e.g. `"49.00"`),
  the same `.toFixed(2)` form the existing refund helper uses. The checkout route
  works in integer cents and has a `moneyFromCents` helper. Do not send cents as
  if they were dollars, that would overcharge by 100x.
- Build a `createTransactionRequest` with `transactionType`
  `authCaptureTransaction` and `payment.opaqueData` set from the token.
- On approval (responseCode `1`): return success with `transId`, and the safe
  fields the gateway returns (AVS response, CVV response, account last-4, account
  type).
- On decline or error: return a failure with a clean human-readable message. Do
  not throw past the caller.
- Do not wire this into checkout yet.

Then run the typecheck and paste the full output (not a checkmark).

## Phase 2: Backend checkout wiring
1. Add a payment token field (the Accept.js `dataDescriptor` + `dataValue`) to
   the `PlaceOrderRequest` schema in `lib/api-spec/openapi.yaml`, then regenerate.
   Run `pnpm --filter ./lib/api-spec run codegen && git status --short` and paste
   the full output. A clean (empty) `git status --short` after regen is the proof.
   Do not hand-edit any file under a `generated/` folder.
2. In `/checkout`, on the real (non-demo) path, require the payment token.
3. Charge with the Phase 1 function using the server-computed total from this
   flow (the same total the route already computes; see the sequencing note in
   item 6 for exactly where in the order this charge happens).
4. On approval only: finalize the order, insert a `payments` row
   (`paymentMethod` `credit_card`, `status` `completed`, amount = total,
   transactionId = gateway transId, last-4 / card type / AVS / CVV from the
   gateway, rawResponse = gateway json), then run the existing recompute helper so
   `balanceDue` reflects the payment (expected: 0).
5. On decline: do not finalize a paid order, keep the cart intact, return a clear
   error. Report your proposed handling of the decline audit trail (whether to
   record anything, given `payments.orderId` is NOT NULL) rather than assuming.

   by the DB transaction. Report how you order the charge relative to the order
   insert and commit so a card can never be charged without a recorded order (for
   example, charge, and only on approval create the order and record the payment
   in the same commit). Surface this at the gate; do not just pick one silently.
7. Add a read-only public payment-config endpoint that returns the API Login ID,
   the Public Client Key, and the sandbox flag for the frontend. It must NOT
   return the transaction key.
