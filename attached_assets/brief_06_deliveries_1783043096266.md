## Context -- What was already built in Brief 5

Brief 5 built the order status and delivery flow that this section reads from. The following decisions and schema changes from Brief 5 are complete and confirmed. Do not change any of them unless this brief explicitly instructs you to.

**Order statuses in use for deliveries (confirmed slugs):**

- `ready_for_store_delivery` -- order is ready to be delivered by the store's own crew
- `out_for_local_delivery` -- store delivery is in progress today
- `carrier_delivery_update` -- a carrier shipment has been created with a tracking number
- `delivered` -- order is fully delivered (applies to both local and carrier orders)

**Schema added in Brief 5 (already exists in the database):**

- `orders.scheduled_delivery_date` -- type: date, nullable. Staff-entered date for when the store crew will deliver locally. This is NOT a manufacturer or carrier estimated date.
- `orders.scheduled_delivery_time` -- type: text, nullable. Currently a free-text field. This brief changes it -- see Section 0 below.
- `shipments` table columns (post-Brief-5): `id`, `order_id`, `carrier_id`, `tracking_number`, `notes`, `created_at`. The columns `shipped_at` and `delivered_at` were dropped in Brief 5. Do not reference them anywhere in this brief.
- `shipment_items` junction table: `id`, `shipment_id` (FK to shipments, cascade), `order_item_id` (FK to order_items, cascade), `quantity` (int NOT NULL).
- `carriers` table includes `tracking_url_template` (nullable). Join shipments to carriers via `shipments.carrier_id`.

**There is no estimated delivery date from a manufacturer or carrier stored in the system.** Do not invent or look for such a field.

### 0A. Change `orders.scheduled_delivery_time` from free text to a time column

**Why:** The current `scheduled_delivery_time` column is type `text`. This brief requires sorting deliveries by time on both the screen and the printed PDF. Text sorting does not sort times correctly. This change fixes that before the new UI is built.

**What to change:**

Note: The data check for existing `scheduled_delivery_time` values is performed in Step 1 of Section 8 before any code is written. Do not proceed with the steps below until Karen has confirmed the Step 1 findings and given the go-ahead.

1. Alter the `orders.scheduled_delivery_time` column from type `text` to type `time` (PostgreSQL `time without time zone`). The stored value will be the start time of the selected delivery window (e.g. `08:00:00` for the 8-9 AM window).

2. Update the order detail panel (built in Brief 5) wherever `scheduled_delivery_time` is currently displayed or edited. Replace the free-text input with a dropdown picker. The dropdown options and their stored values are:

| Display label | Stored value (time) |
|---|---|
| 8:00 AM - 9:00 AM | 08:00:00 |
| 9:00 AM - 10:00 AM | 09:00:00 |
| 10:00 AM - 11:00 AM | 10:00:00 |
| 11:00 AM - 12:00 PM | 11:00:00 |
| 12:00 PM - 1:00 PM | 12:00:00 |
| 1:00 PM - 2:00 PM | 13:00:00 |
| 2:00 PM - 3:00 PM | 14:00:00 |
| 3:00 PM - 4:00 PM | 15:00:00 |
| 4:00 PM - 5:00 PM | 16:00:00 |
| 5:00 PM - 6:00 PM | 17:00:00 |

3. The dropdown must have a blank default option (no time selected). Selecting the blank option stores NULL. The field remains optional -- staff are not required to set a delivery time.

4. Wherever `scheduled_delivery_time` is displayed as a read-only value in the UI (order detail, any status panels), display the human-readable label (e.g. "2:00 PM - 3:00 PM"), not the raw time value. If null, display "Not set".

5. Do not change anything else about the order detail panel or any other Brief 5 work. Only the `scheduled_delivery_time` field changes.

## Section 3 -- Local Deliveries tab

This tab shows only incomplete local delivery orders. Completed (delivered) orders do not appear here.

### 3A. Which orders appear here

Pull all orders where `orders.status` is one of:

- `ready_for_store_delivery`
- `out_for_local_delivery`

The status `delivered` does NOT appear in this tab under any circumstances.

### 3B. Columns to display

The Local Deliveries table must match the visual layout and column data of the existing Orders list page exactly, with two additions at the left side: a checkbox column and a Scheduled Date/Time column. Staff are already familiar with the Orders list layout -- do not rearrange or rename any of the standard columns.

Column order, left to right:

| Column label | Source |
|---|---|
| (Checkbox) | Checkbox input for selecting this order. No column header label. See Section 3F. |
| Scheduled Date/Time | Two lines stacked in one cell: line 1 is `orders.scheduled_delivery_date` formatted as a short readable date (e.g. "Thu, Jul 3, 2026") -- if null display "Not scheduled". Line 2 is `orders.scheduled_delivery_time` displayed as the human-readable window label (e.g. "2:00 PM - 3:00 PM") using the mapping from Section 0A -- if null display "Not set". |
| Order # | The `ORD-` prefixed order reference. Clickable link to the order detail page using the same link pattern as the existing Orders list. |

|---|---|

### 3D. Filters

### 3E. Default sort

Default sort: `orders.scheduled_delivery_date` ascending, NULLs last. Then by `orders.scheduled_delivery_time` ascending, NULLs last within the same date. This sort is fixed -- do not add column header click-to-sort functionality.

### 3F. Checkbox selection and delivery manifest printing

This feature is on the Local Deliveries tab only. It does not appear on the Direct Ship or Completed tabs.

**Checkboxes**

Add a checkbox to the left of every row in the Local Deliveries table. There is no Select All checkbox. Staff select orders individually by checking one or more boxes. Any order visible in the tab can be checked regardless of its scheduled date or whether it has a scheduled time set. Checkboxes persist their state while the staff user is on this tab. Navigating to another tab and returning clears the selection.

**Generate Delivery Manifest button**

Add a button above the table labeled: **Generate Delivery Manifest**

This button is only clickable when at least one checkbox is selected. When no checkboxes are selected, the button is grayed out and cannot be clicked. When clicked, this button generates two separate PDFs -- one Manifest Summary and one merged Delivery Copies document -- and opens each in its own new browser tab. Both PDFs are generated server-side as streaming route responses with `Content-Type: application/pdf`. Do not use signed blob URLs or time-limited download links.

**Document 1 -- Delivery Manifest Summary**

A single-page summary document listing all checked orders. Layout and content:

- Page size: US Letter (8.5" x 11"), portrait, 1-inch margins on all sides.
- Header: "Oasis Garden and Patio -- Delivery Manifest" in bold.
- Subheader: "Total deliveries: [N]" where N is the number of checked orders.
- One row per checked order containing:
  - Order number
  - Customer name
  - Customer shipping address -- use the shipping address fields from the order, not the billing address. There may be two addresses on an order (shipping and billing); always use the shipping address. Use the exact same fields the existing order detail page displays in the Shipping section of the right panel. Do not guess column names.
  - Scheduled delivery date -- formatted as a readable date (e.g. "Thu, Jul 3, 2026"). If null, display "Not scheduled".
  - Scheduled delivery time -- display the human-readable window label (e.g. "2:00 PM - 3:00 PM"). If null, display "Time not set".
  - Order total
- Rows sorted by `orders.scheduled_delivery_date` ascending then `orders.scheduled_delivery_time` ascending, NULLs last on both.
- Minimum 11pt font for all body rows. Keep the layout clean and readable. This is a driver and sales agent reference sheet for loading the truck.

**Document 2 -- Merged Delivery Copies**

A single merged PDF containing the Delivery Copy of each checked order, one order per section, in the same sort order as the manifest (by `scheduled_delivery_date` ascending then `scheduled_delivery_time` ascending, NULLs last on both). All checked orders are included regardless of whether they have a scheduled date or time -- orders without a date or time appear at the end.

The Delivery Copy for each order is the same document already generated by the existing print system on the order detail page (the "Delivery copy" checkbox option visible when staff click the Print button on an order). Do not rebuild or redesign this document. Use the exact same generation logic that already exists for the Delivery copy.

To produce the merged PDF:
- Identify the existing server-side function or route that generates the Delivery copy PDF for a single order.
- Call that function once per checked order, in sort order.
- Merge the resulting PDF pages into a single PDF document.
- Use whatever PDF merging capability is available in the existing PDF library already in the project. Do not install a new library for this.

If the existing Delivery copy generation logic cannot be reused directly (for example, if it is tightly coupled to a browser print event rather than a server route), stop and flag this to Karen before proceeding. Do not attempt to rebuild the Delivery copy document from scratch.

**Browser popup behavior**

Opening two new tabs simultaneously may be blocked by some browsers as a popup. To handle this reliably, open Document 1 (the Manifest Summary) immediately on button click, then open Document 2 (the Merged Delivery Copies) immediately after. Both should open within the same user gesture so browsers treat them as intentional. If the agent is aware of a more reliable cross-browser approach for opening two tabs from a single button click within the Next.js stack already in use, use that approach and note it in the check-in report.

## Section 4 -- Direct Ship tab

This tab shows only incomplete direct ship orders. Completed (delivered) orders do not appear here.

### 4A. Which orders appear here

Pull all orders that meet BOTH of these conditions:

1. `orders.status` = `carrier_delivery_update` only. The status `delivered` does NOT appear in this tab.
2. The order has at least one record in the `shipments` table where `tracking_number` IS NOT NULL.

If an order has more than one shipment record, display one row per shipment, not one row per order. The order number column must appear on every row so staff can see which order each shipment belongs to.
