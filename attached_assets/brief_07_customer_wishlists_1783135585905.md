## Overview

This brief covers four interconnected pieces of work:

1. **Schema** -- new database tables and two new columns to support persistent wishlists for logged-in customers and a site-wide marketing contact preference per customer account.
2. **Customer account settings** -- a new marketing contact preference toggle on the customer-facing account page.
3. **Automated wishlist email** -- a one-time transactional/disclosure email sent via Resend the first time a logged-in customer saves any item to their wishlist.
4. **Staff UI** -- a Customer Wishlists section under Sales > Customers in the staff portal, including a read-only opt-out indicator in the existing customer modal and a manual reach-out email tool.

Guest wishlists stored in browser local storage are entirely out of scope. This system only applies to customers with a logged-in account.

## Environment variable requirement -- read before writing any code

All customer-facing URLs generated by the system (email links, opt-out links, account settings links, confirmation page links) must be built using a base URL pulled from an environment variable. Do not hardcode any domain.

Add or confirm the existence of a `BASE_URL` environment variable in the Replit environment. All generated links must use this variable as their root.

Example pattern:
```
const baseUrl = process.env.BASE_URL;
const optOutLink = `${baseUrl}/account/preferences/opt-out?token=${signedToken}`;
```

This is required because the site currently runs on a replit.app domain and will be migrated to oasisgardenandpatio.com via DNS transfer at launch. A single environment variable update must be all that is needed to update every link in every email after that migration. Hardcoded domains will break at launch.

All columns for this table are defined here. Do not split the migration across steps.

| Column | Type | Notes |
|---|---|---|
| `id` | serial primary key | |
| `customer_id` | integer, not null | Foreign key to customer accounts table (use exact table and column name from Step 1 report). On delete cascade. |
| `product_id` | integer, not null | Foreign key to `products.id`. On delete cascade. |
| `added_at` | timestamptz, not null | Default `now()`. Store in UTC. Display in Pacific Time in the staff UI. |

Do NOT add a unique constraint on `(customer_id, product_id)`. The existing wishlist implementation allows a customer to save the same product multiple times with different variants (for example, different finishes or fabrics). Karen will confirm unique constraint instructions as part of the Step 1 sign-off.

### 2B. New columns: `marketing_opt_out` and `marketing_opt_out_at` on the customer accounts table

Add the following columns to the customer accounts table (use exact table name from Step 1 report).

| Column | Type | Notes |
|---|---|---|
| `marketing_opt_out` | boolean, not null | Default `false` (opted in -- contact is permitted by default). Null is not permitted. |
| `marketing_opt_out_at` | timestamptz, nullable | Null when opted in. Set to current timestamp when the customer opts out (via opt-out link or account settings toggle). Reset to null if the customer opts back in. |

The `marketing_opt_out` column controls:
- Whether the automated wishlist disclosure email is sent when a customer saves their first wishlist item.
- Whether staff can send a reach-out email from the wishlist UI.
- Future marketing blast emails (not built in this brief, but this column will serve that purpose).

This opt-out does NOT affect order confirmation emails, order status emails, shipping updates, delivery notifications, or any other emails tied to a purchase transaction. Those always send regardless of this flag. Do not add any opt-out check to those email flows.

### Opt-out link implementation

The opt-out link must use a signed token. Do not use a raw customer ID in the URL.

- Generate a signed token encoding the customer ID with a 30-day expiry. 30 days is required to comply with CAN-SPAM, which mandates that opt-out mechanisms remain functional for at least 30 days after the email is sent.
- When the customer clicks the link: validate the token, set `marketing_opt_out = true`, redirect to a confirmation page.
- Confirmation page copy: "Got it -- we will not contact you about your wishlist or send you promotional emails. You can update this preference any time in your account settings."
- If the token is expired or invalid, show: "This link has expired. You can update your marketing contact preference any time in your account settings." Link the phrase "account settings" to the account settings page.
- Build the opt-out URL using `BASE_URL` from the environment variable as described at the top of this brief.

**Pricing rules -- two layers, strictly enforced:**

This is critical. The wishlist detail view is staff-only, so staff always see price data if it exists. However, the pricing rules must also flow correctly to the customer-facing wishlist view and the reach-out email.

- *Staff UI (this view):* Always show the sale price if it exists in the product database, or MSRP if no sale price, regardless of whether the product is in inquiry/call-for-pricing mode on the storefront. If no price exists in the database at all, show "--".
- *Customer-facing wishlist view:* Apply the exact same pricing visibility rules as the storefront. If the product has `show_price_online = true`, show the price. If the product is in inquiry mode (`show_price_online = false`), show nothing -- no price, no placeholder. The customer sees no price information that they would not see on the regular product page.
- *Reach-out email (Step 6):* Follow the customer-facing rule. Do not include prices for inquiry-mode products in the email sent to the customer.
- `price_at_save` in the schema records the price as it was at save time for storefront-visible products only. For staff display, always read the live price from the product database -- do not rely on `price_at_save` for the staff UI. If the product no longer exists or has no price in the database, show "--". `price_at_save` is reserved for the future order conversion feature only and must not be displayed anywhere in the staff UI or customer-facing views.

**Customer-facing wishlist page disclaimer:** At the bottom of the customer-facing wishlist page, display the following text in small muted styling (below the items list, above the page footer):

"Prices and availability are subject to change. Wishlist prices reflect current pricing and are not guaranteed. Product availability is subject to change at the manufacturer's discretion. For a firm price quote, please contact us -- quotes are honored for 30 days from the date of issue."

This text must appear on the customer-facing wishlist page only. Do not show it on the staff wishlist detail view.
